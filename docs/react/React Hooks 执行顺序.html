执行流程总览

先把这条线背下来。后面的源码名词很多，但都能归到这条 commit 主线里。

Render：执行组件，记录 hooks ↓ Before Mutation：读取 DOM 快照 ↓ Mutation：DOM 变更 + useInsertionEffect ↓ useLayoutEffect（同步，DOM 更新后、绘制前） ↓ 浏览器绘制（通常发生在这里） ↓ useEffect（Passive：通常 Paint 后，也可能被同步 flush）

三个 Hook 的核心差异

使用时先问一个问题：这个副作用要不要阻塞浏览器绘制？如果不需要，默认放进 useEffect。

useInsertionEffect

同步
  • 执行：同步，直接调用
  • 时机：commit mutation 阶段，早于 layout effects；不要假设早于所有 DOM 更新
  • DOM 访问：不要依赖（ref.current 尚未 attach）
  • 作用：给 CSS-in-JS 提前注入样式，避免样式闪动
useInsertionEffect(() => {
  const style = document.createElement("style");
  style.textContent = "body { color: blue; }";
  document.head.appendChild(style);
}, []);

关键路径

// ReactFiberCommitWork.js
commitMutationEffects()
  -> commitReconciliationEffects()           // Placement / DOM 变更
  -> commitHookEffectListUnmount(HookInsertion)
  -> commitHookEffectListMount(HookInsertion) // useInsertionEffect
  -> commitHookLayoutUnmountEffects()

useLayoutEffect

同步
  • 执行：同步，直接调用
  • 时机：DOM 更新后、浏览器绘制前
  • DOM 访问：可用
  • 风险：会阻塞绘制，逻辑过重会拖慢首屏
  • 作用：测量布局、同步修正 UI，减少可见闪烁
useLayoutEffect(() => {
  const height = ref.current?.offsetHeight;
  setHeight(height);
}, []);

关键路径

commitMutationEffects()  -> DOM 更新
root.current = finishedWork
commitLayoutEffects()    -> useLayoutEffect
flushSpawnedWork()       -> 标记 pending passive effects

useEffect

异步
  • 执行：Passive effect，不在 render 阶段执行
  • 时机：通常在浏览器绘制后；但 pending passive effects 可能在下一次同步工作前被提前 flush
  • 调度：Scheduler；浏览器环境通常用 MessageChannel，其他环境可能用 setImmediate / setTimeout
  • DOM 访问：可用，普通异步路径不阻塞本次绘制
  • 作用：请求、订阅、日志、定时器等副作用
useEffect(() => {
  fetchData();
}, []);

回调收集（render / commit）

// Render Phase:
useEffect 通过 pushSimpleEffect 记录到 fiber.updateQueue
依赖变化时带上 HookHasEffect | HookPassive

// Commit Phase:
commitRoot 发现 PassiveMask 后调度 flushPassiveEffects
layout 阶段后把本次提交标记为 PENDING_PASSIVE_PHASE

回调执行（Scheduler 触发）

scheduleCallback(..., flushPassiveEffects)
  -> 浏览器中通常由 MessageChannel 触发
  -> flushPassiveEffects()
  -> commitPassiveUnmountEffects() // 先 cleanup
  -> commitPassiveMountEffects()   // 再 create

// 但同步更新路径会主动提前执行：
performSyncWorkOnRoot() -> flushPendingEffects()

一句话：useEffect 回调先被收集，再由 flushPassiveEffects 执行；通常晚于 Paint，但源码并不保证永远晚于 Paint。

普通异步路径时间线（示意）

这是最常见、也最适合初学者建立直觉的路径。下面的时间只是示意，不代表固定耗时。

开始
0.1 ms DOM mutation
+ insertion
0.2 ms useLayoutEffect
（同步）
0.3 ms 浏览器
开始绘制
1.5 ms MessageChannel

1.6 ms useEffect

结论：普通路径下 useEffect 相比前两个 Hook 更晚，通常在绘制后执行；但同步更新、离散事件更新或下一次同步 render 开始前，React 可能先把 pending passive effects flush 掉。

最短记忆版

把这三句话记下来，基本就不会在日常开发里选错 Hook。

▲
useInsertionEffect
最早的 effect，给样式系统用，不依赖 DOM。
▶
useLayoutEffect
中间，同步，读写布局但会阻塞绘制。
▼
useEffect
通常最晚，大多数副作用优先用它。

一句话结论

这些结论都来自上面的源码路径，适合当作面试或复盘时的短答案。

  • useLayoutEffect 中 setState：本轮 commit 正常结束 → React 在 Paint 前同步处理新更新 → 用户通常只看到最终画面。
  • useEffect 中 setState：普通异步路径下更晚触发，可能让用户先看到上一帧；但离散事件或同步路径下，passive effects 也可能被提前 flush。
  • useInsertionEffect：官方约束是不要调用 setState；DEV 下源码会给出 useInsertionEffect must not schedule updates. 警告。

源码定位（React 19.2.6）

不用一上来读完整源码，先记住下面四个入口。每个入口负责一个问题。

  • Hook 收集：ReactFiberHooks.js 中的 mountEffectImpl / updateEffectImpl 调用 pushSimpleEffect，把 effect 放进 fiber.updateQueue 的环形链表。
  • 依赖比较：areHookInputsEqual 逐项用 Object.is 比较依赖项；[] 和下一次 render 创建的新 [] 仍然相等，因为没有任何一项不同。
  • Insertion/Layout 提交：ReactFiberCommitWork.js 在 mutation 阶段处理 HookInsertion，在 layout 阶段处理 HookLayout。
  • Passive 提交：ReactFiberWorkLoop.js / ReactFiberRootScheduler.js 通过 flushPassiveEffects / flushPendingEffects 执行 HookPassive。

深入：useLayoutEffect 中调用 setState

场景：<A><B><C></C></B></A>，B 同时有 useLayoutEffect（触发 setState）和 useEffect。下面从更新任务视角看整个过程。以下默认生产模式、非 StrictMode；DEV StrictMode 会额外模拟卸载/挂载 effect。

关键理解

  • 任务 1 的 DOM 更新已经生效了（commitMutation 已执行），但通常还没 Paint。
  • 任务 2 是新一轮 root work，不是在任务 1 里"修补"；React 会重新从 root 调度，但子树可以 bailout。
  • 任务 2 的 DOM 更新会覆盖任务 1 的可见结果——两次 mutation 都在 Paint 之前完成时，用户看到的只是最终状态。
  • 任务 1 没有被"丢弃"——它的 commit 跑完了，只是最终被任务 2 的结果覆盖了。

B 的 useEffect 调用链

B 同时有 useLayoutEffect（触发 setState）和 useEffect。
核心问题：任务 2 的 render 前为什么要先执行掉任务 1 的 useEffect？

先看调用栈：pending passive effects 如何被同步更新截胡

// 以下是关键顺序；是否经过 MessageChannel 取决于当前路径

commitRoot(任务 1)
  ├── scheduleCallback(NormalPriority, flushPassiveEffects)
  ├── commitMutationEffects()
  ├── root.current = finishedWork
  ├── commitLayoutEffects()
  │   └── B.useLayoutEffect() → setState(1)
  ├── flushSpawnedWork()
  │   └── pendingEffectsStatus = PENDING_PASSIVE_PHASE
  └── flushSyncWorkOnAllRoots()
      └── performSyncWorkOnRoot(任务 2)
          ├── flushPendingEffects()
          │   ├── commitPassiveUnmountEffects()
          │   └── commitPassiveMountEffects()
          ├── renderRootSync()
          └── commitRoot(任务 2)

// 所以：任务 1 的 useEffect 不是在任务 2 的 commit 中途才跑，
// 而是在任务 2 render 开始前，由 performSyncWorkOnRoot 主动清空。

为什么 React 要在新同步任务前 flush？

  • 因为 passive effects 会影响后续工作。flushPassiveEffectsImpl 最后会调用 flushSyncWorkOnAllRoots，passive effect 里也可能继续 setState。
  • React 在同步工作入口主动清空。performSyncWorkOnRoot 会先调用 flushPendingEffects；如果确实 flush 了 passive effects，就返回外层调度器重新计算优先级。
  • 这不是“commit 开头”的固定步骤。commitRoot 自身开头也会循环 flush pending effects，但 layout effect 触发的同步更新，关键入口是 performSyncWorkOnRoot → flushPendingEffects。

B 的 useEffect 实际执行了几次？

  • 第 1 次：任务 2 render 前，performSyncWorkOnRoot → flushPendingEffects 执行任务 1 留下的 passive effect；闭包来自任务 1 render。
  • 是否有第 2 次：取决于任务 2 的 useEffect 是否带 HookHasEffect。如果没有依赖数组，或依赖变了，会再次执行；如果是 []，更新时依赖相等，不会再次执行。
  • 如果 useEffect 里有 setState：这次更新会在 passive 阶段结束后由 flushSyncWorkOnAllRoots 继续处理。

实际代码走读：deps 为 []

以 Counter 组件为例，count 初始值为 0。重点看两个事实：useLayoutEffect 的 [] 只在首次挂载执行；useEffect 的 [] 在第 2 轮 render 时会被判定为依赖相等，因此不会收集新的 passive create。

function Counter() {
  const [count, setCount] = useState(0);

  useLayoutEffect(() => {
    console.log("[ useLayoutEffect ] ===>");
    setCount(1);
    return () => { console.log("[ useLayoutEffect cleanup ] ===>"); };
  }, []);

  useEffect(() => {
    console.log("Counter component updated");
    console.log("[ count ] ===>", count);
    return () => { console.log("[ useEffect cleanup ] ===>"); };
  }, []);
}
// ══════ 第 1 轮（mount，count = 0）══════════════════════

Render：Counter 执行，count = 0
Commit：
  DOM 更新
  useLayoutEffect create：① "[ useLayoutEffect ] ===>" → setCount(1) 入队
  标记 pending passive effects（useEffect 还没跑）

// Paint 前发现有同步工作 → performSyncWorkOnRoot()
// 进入新 render 前先 flushPendingEffects()

flushPendingEffects()：
  ② "Counter component updated"
  ③ "[ count ] ===> 0"              // 闭包来自第 1 轮 render

// ══════ 第 2 轮（update，count = 1）═════════════════════

Render：Counter 重新执行，count = 1
  useLayoutEffect deps [] 与上次相等 → 不带 HookHasEffect
  useEffect deps [] 与上次相等 → 不带 HookHasEffect

实际控制台输出（同步阶段）

① [ useLayoutEffect ] ===>
② Counter component updated
③ [ count ] ===> 0              // 第 1 轮闭包
// 第 2 轮只更新 DOM，不会再次执行 [] 的 layout/effect

关键发现

  • [] 不会因为“新数组引用”而失效。areHookInputsEqual 比较的是数组里的每一项；空数组没有任何一项不同，所以更新时相等。
  • useEffect 实际跑 1 次。它可能被 layout effect 触发的同步更新提前到 Paint 前执行，但闭包仍来自第 1 轮 render，所以打印 count = 0。
  • 第 2 轮不会重新执行 layout effect。useLayoutEffect(..., []) 依赖相等，更新阶段不带 HookHasEffect，因此不会再次 setCount。
  • 想观察 count=1 的 effect，要把 count 放进依赖数组。例如 useEffect(..., [count]) 会在第 2 轮收集新的 passive effect。
