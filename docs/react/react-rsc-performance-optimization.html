React RSC 性能优化深度解析

通过 RSC + SSG 将 React 性能推向极限的架构思路，以及冷静的批判性分析

01 背景：一个"意外发现"

灵感来源

作者封装了一个 <Show> 组件做条件渲染，评论区有人指出：即使 when 为 false，子组件仍会执行一次。

Show 组件封装 JSX 
// 封装前：冗长的条件判断
{isShow && (
  <>
    <div className='border-b mt-20 mb-8'></div>
    <Giscus />
  </>
)}

// 封装后：语义化
<Show when={state.count > 0} fallback={<div>Loading...</div>}>
  <div>My Content</div>
</Show>
核心洞见

"提前执行"不就是静态提升（Static Hoisting）吗？如果把这段代码放到 RSC + SSG 中，运行时不该执行的逻辑会在构建时执行，被打包成静态 HTML 和 RSC Payload。

02 核心：RSC + SSG 如何改变渲染流程

传统 CSR 渲染流程

→

→

RSC + SSG 渲染流程

构建时执行 ✨
→
生成 HTML
→
生成 RSC Payload
→
浏览器解析 JSON
→
0 成本生成 Fiber
→
DOM 已存在 ✅
对比维度 传统 React (CSR) RSC + SSG
执行时机 运行时 构建时
数据格式 JavaScript 执行 RSC Payload (类 JSON)
解析速度 基准 ~10x（JSON vs JS）
DOM 创建 客户端创建 服务端已生成
Hydration 成本 高（全量） 极低（仅绑定事件）
Diff 复杂度 O(n) 全量 O(n) 但 n 极小 + 完美缓存命中

03 关键手法：状态与 UI 分离

核心思路：把客户端组件中只有数据逻辑的部分抽成独立组件（无 DOM），让父组件变成纯服务端组件。

优化前：整个组件是客户端组件 客户端组件 
'use client'
function Banner() {
  const { data } = useQuery('/api/xxx')

  return (
    <div>
      <h1>xxxxx</h1>
      <p>这里包含大量静态文本...</p>
      <div>订阅人数：{data}</div>
    </div>
  )
}
⬇
优化后：父组件变为服务端组件 服务端组件 
import Counter from './counter'

// 默认为服务端组件，可被静态渲染
function Banner() {
  return (
    <div>
      <h1>xxxxx</h1>
      <p>这里包含大量静态文本...</p>
      <div>订阅人数：<Counter /></div>
    </div>
  )
}
counter.tsx — 纯数据组件，零 DOM 客户端组件 
'use client'
function Counter() {
  const { data } = useQuery('/api/xxx')
  return <>{data}</>
}
关键理解

Counter 组件在底层实现上，代表的不是一个组件身份，而是一个状态身份。它连一个 div 都没有，只是一个纯粹的数据结果。

04 进阶：多字段场景的处理

当一个组件有多个字段依赖同一接口时，使用 zustand（替代 Context 避免 re-render）+ 状态提升/下放模式。

服务端组件 — 纯静态内容 服务端组件 
import { SubscribeRoot, Counter, State } from './subscribe'

function Banner() {
  return (
    <SubscribeRoot>
      <h1>xxxxx</h1>
      <p>这里包含大量静态文本...</p>
      <div>订阅人数：<Counter /></div>
      <div>是否订阅：<State /></div>
    </SubscribeRoot>
  )
}
客户端组件 — 纯数据逻辑，零 DOM 客户端组件 
'use client'
import { useSubStore } from './store'

export function Counter() {
  const counter = useSubStore((state) => state.counter)
  return <>{counter}</>
}

export function State() {
  const isSubscribe = useSubStore((state) => state.isSubscribe)
  return <>{isSubscribe ? 'yes' : 'no'}</>
}

优化后的完美拆分

服务端组件 = 全是静态内容，零动态逻辑 客户端组件 = 全是数据逻辑，零 DOM 元素

为什么选 Next.js

纯粹的服务端组件往往比同构组件拥有更好的开发体验。先服务端组件提供默认值，再客户端组件提供交互能力，更符合对完美框架的构想。且服务端组件优先可以在包体积上做到极致优化。

06 意外关联：shadcn/ui 的设计哲学

shadcn/ui 的 Headless 模式

export function ContextMenuDemo() {
  return (
    <ContextMenu>
      <ContextMenuTrigger className="flex ...">
        <span>Right click here</span>
      </ContextMenuTrigger>
      ...
    </ContextMenu>
  )
}

ContextMenuTrigger 在没有控制状态的情况下让弹窗显示——它本身就代表了一个状态变化，可以是非常纯粹的动态数据逻辑处理，无需包含任何 DOM 元素内容。

作者的结论

shadcn/ui + Next.js 是"绝配"。借助这个思路，可以在 Next.js 中做到不输 Vue 3.6、不输 SolidJS 的极致性能。

07 冷静分析：值得商榷的地方

"逼近物理极限"过于夸张

文中 1ms 100 万次 diff 的测试数据没有给出测试条件和代码，无法验证。且 diff 速度从来不是 React 的瓶颈，网络请求、布局计算、绘制才是。

"超越 SolidJS"缺乏实证

文中提到的 Lighthouse 分析截图没有展示具体数据，且 Lighthouse 分数受很多因素影响，不能单凭此下结论。

"状态下沉"模式的适用范围被高估

该模式适用于"大量静态内容 + 少量动态数据"的场景（如营销页、博客），但对重交互应用（后台管理、实时协作工具）几乎不适用，因为大量 DOM 本身就是动态的。

shadcn/ui 的设计初衷并非性能优化

headless 组件的核心价值是可定制性和无样式约束，将其解读为"Next.js 性能标杆型实现"是过度诠释。

忽略了 RSC 的实际复杂性

RSC 的 streaming、suspense 边界、客户端组件的交互延迟等实际问题，文章完全没有涉及。

与 Solid 的根本性差异未被正视

Solid 的优势在于 signal 的细粒度响应式（无需 re-render 整个组件），而 React 即使使用了 RSC，客户端组件仍然是组件级 re-render，这是根本性差异，不能靠架构手法抹平。

08 有价值的观点总结

RSC + SSG 确实能大幅减少客户端 JS 执行量

这是 React 团队和 Next.js 团队的核心卖点，方向正确。

动态逻辑最小化、下沉到叶子节点

合理的优化策略，符合 React 的设计哲学。

框架选型的分析有参考价值

同构 vs 服务端优先的对比，对技术选型有启发。

"组件即状态"的抽象思路

把客户端组件抽象为纯数据载体，是一种值得尝试的架构模式。
